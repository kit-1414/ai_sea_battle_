## Введение

В докладе мы рассмотрим на примере тестового приложения «Морской бой», каким образом OpenCode предлагает работать с ИИ.

- Приложение «Морской бой».
  Написаны два агента, которые реализуют алгоритм классической игры «Морской бой».
  Это приложение состоит только из сущностей, которыми оперирует OpenCode, и не содержит ни строки кода в привычном понимании.
  Данный проект служит иллюстрацией того, какие сущности есть в OpenCode для работы с ним.

### Приложение «Морской бой»

Приложение «Морской бой» представлено в трех версиях:

- версия 1 — максимально произвольная файловая структура, вся конфигурация OpenCode представлена в `opencode.json`;
- версия 2 — файловая структура максимально адаптирована для OpenCode, в `opencode.json` оставлено только необходимое;
- версия 3 — модифицированная версия 2, в которой с помощью ИИ была оптимизирована логика приложения: минимизированы вызовы агентов и т. п.

Наибольший интерес представляет первый проект, где вся конфигурация проекта находится в одном файле, поэтому все варианты сущностей видны сразу, а именно:

- `instructions` — файлы инструкций (правил и навыков), которые сразу загружаются в контекст при запуске OpenCode;
- `agents` — файлы агентов и субагентов. Агенты могут использоваться для запуска новой сессии OpenCode, принимать параметры или переключать контекст работы. Они доступны через `@`;
- `commands` — команды, доступные для вызова через `/`. Они служат для запуска агентов с параметрами, аналогично скриптам запуска приложений с аргументами. Примеры встроенных команд: `/build` и `/plan`.

### Контекст

В OpenCode (или в ИИ в целом) есть понятие контекста — набора знаний, инструкций и загруженных исходных файлов, в рамках которого ИИ выполняет работу.

Контекст существует в рамках сессии: он хранится в ней и меняется в процессе работы. Таким образом, сессия — это контейнер контекста.

Новая сессия создается каждый раз при запуске агента или субагента, в том числе при запуске OpenCode: пользователь запускает его с определенным агентом.

Агент или субагент при запуске наследует сессию родителя и обогащает свою сессию данными в процессе работы или выполнения команд пользователя.

При завершении работы агента его сессия либо уничтожается, либо сохраняется с определенным ID, по которому ее можно снова вызвать. Тогда агент начнет работу с уже сохраненным контекстом.

Агенты могут общаться между собой по принципу взаимодействия вызывающей и вызываемой функций: с помощью аргументов и результата, возвращаемого в конце работы. Содержимое дочерней сессии недоступно родительской.

При необходимости можно организовать обмен данными через внешние файлы, системы наподобие RabbitMQ и т. п.

### Где хранится контекст сессии

Где хранится контекст сессии: локально или удаленно?

LLM (например, ChatGPT) хранит только рабочий срез контекста — последние сообщения, которые помещаются в промпт.
Это временное хранение: модель не «помнит» за пределами текущего окна токенов.
Ограничение: если история слишком длинная, агент должен сам решать, какой кусок передать в LLM.

Память LLM ограничена окном токенов.
Модель видит только те сообщения, которые агент передает ей в текущем запросе.
После завершения вызова она ничего не «помнит» — контекст не сохраняется в облаке автоматически.

LLM не хранит контекст агента на сервере между вызовами.

### Conversation API
Conversation API — это интерфейс, который позволяет разработчикам создавать многоканальные диалоги (чат, SMS, WhatsApp, голос) с сохранением контекста и списка участников, а также управлять ими. Сама LLM не хранит историю между вызовами, поэтому Conversation API обеспечивает управление состоянием и маршрутизацию сообщений.

Conversation API — обертка вокруг LLM.
LLM не хранит контекст между вызовами — этим занимается агент или Conversation API.

В OpenCode или других фреймворках именно Conversation API отвечает за то,
чтобы субагенты и LLM работали с единым контекстом.

Conversation API не существует «где-то абстрактно» — он запускается на облачных серверах провайдера
(например, Twilio или Google Cloud), и именно там обрабатываются и сохраняются данные диалога.
По умолчанию используется глобальный дата-центр, но можно выбрать региональные узлы.

Для этого и существует Conversation API: он позволяет продолжить работу в одной и той же сессии даже с другого компьютера или устройства.

Каждая сессия имеет уникальный идентификатор. Если вы подключаетесь с другого компьютера, достаточно указать этот ID, и Conversation API вернет историю и текущее состояние диалога.
Для этого нужно использовать Conversation ID и авторизацию с помощью API-ключа, отправив REST-запрос по URL конкретного дата-центра.

Отправляем запрос на создание новой беседы:

```http
POST /v1/Conversations
Authorization: Bearer <API_KEY>
Content-Type: application/json
```

```json
{
  "unique_name": "support_chat"
}
```

В ответе придет объект с полем `sid` — это и есть Conversation ID.

Использование Conversation ID на другом компьютере.
Теперь, имея `sid`, можно подключиться к той же беседе:

```http
GET /v1/Conversations/CHXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX/Messages
Authorization: Bearer <API_KEY>
```

Этот вызов вернет все сообщения диалога, и можно будет продолжить работу с того места, где она была остановлена.

Данные беседы (Conversation ID) хранятся в облаке ограниченное время:

- в Google Cloud Conversational Analytics API — до 180 дней без активности, после чего они автоматически удаляются;
- в Twilio Conversations API — пока вы сами не удалите беседу.

После удаления у обоих провайдеров действует «мягкий» период хранения длительностью около 30 дней, после чего данные стираются окончательно.

### Инструкции

Файлы содержат знания, правила и описания: бизнес-логику проекта, правила написания кода и любые текстовые сведения, на основе которых ИИ должен анализировать или действовать (изменять файлы, выполнять расчеты или взаимодействовать с другими системами).

Они могут загружаться сразу при запуске OpenCode, по команде пользователя в текущем контексте либо агентами для получения необходимого им рабочего контекста.

### Агенты

Агент — это стартовая точка новой сессии OpenCode. В нее загружаются необходимые правила и инструкции, а затем в ее рамках выполняется определенная работа.

Ключевой момент — создание новой отдельной сессии при запуске агента.

Агенты бывают двух видов: основные агенты и субагенты (`mode: primary | subagent`). Субагент может быть запущен другим агентом.

Пользователю доступны только публичные агенты и субагенты с атрибутом `hidden: false`.

В конфигурации видно, что для агента можно:

- задать стартовый промпт, указать файл с расширенным текстом промпта, перечень загружаемых инструкций и т. п.;
- настроить `permission` — перечень инструментов и атрибутов, определяющих, разрешен ли инструмент и, если разрешен, какие ресурсы ему доступны.

При настройке прав приоритет имеют последние правила. Например, можно сначала перечислить общие запреты, а затем добавить частичные разрешения или исключения.

### Передача контекста от агента к субагенту

Когда агент вызывает субагента, контекст автоматически не передается.
Передаются только конкретные параметры и данные в заданной структуре.

Но в OpenCode есть возможность сериализовать и передать весь контекст от агента к субагенту.
Можно сформулировать это в промпте: «При вызове передай контекст», но это не дает стопроцентной гарантии, что так и будет.

Для гарантии задаем это в конфигурационном файле `opencode.json`:

```jsonc
{
  "agent": {
    "name": "А",
    "description": "Основной агент, который управляет задачами и вызывает субагентов",
    "settings": {
      "language": "ru",
      "tone": "neutral",
      "auto_context": true, // глобальная настройка: всегда прикладывать контекст
      "context_field": "context" // имя поля, куда сериализуется контекст
    },
    "subagents": {
      "Б": {
        "name": "Б",
        "description": "Субагент для анализа текста",
        "auto_context": true, // включаем автоматическую передачу контекста
        "context_field": "context", // поле, куда будет подставлен сериализованный контекст
        "tasks": {
          "analyze_text": {
            "args": ["input"],
            "returns": ["result", "context_update"]
          }
        }
      }
    }
  }
}
```

### Передача параметров и возврат результата между агентом и субагентом

#### Передача параметров и аргументов
Основной агент вызывает субагента через API или внутренний вызов.

Параметры и аргументы передаются в структурированном формате, чаще всего в виде JSON-объекта.

Пример:

```json
{
  "task": "analyze_text",
  "input": "Пример текста",
  "options": {
    "language": "ru",
    "mode": "summary"
  }
}
```

#### Получение ответа от субагента

Субагент обрабатывает входные данные и возвращает результат также в формате JSON.
Ответ обычно содержит:

- `status` (успех/ошибка);
- `result` (основной результат выполнения);
- `metadata` (дополнительная информация: время выполнения, статистика, логи).

Пример:

```json
{
  "status": "success",
  "result": "Краткое содержание текста",
  "metadata": {
    "tokens_used": 120,
    "execution_time_ms": 45
  }
}
```

#### Формат обмена
JSON — стандартный формат, так как он легко сериализуется/десериализуется и поддерживается большинством языков.
Иногда для более компактной передачи используются Protobuf или MessagePack, если важны скорость и экономия ресурсов.
Канал передачи может быть следующим:

- внутренний вызов (функция/метод) — по умолчанию;
- HTTP/gRPC-запрос;
- сообщение в очереди (Kafka, RabbitMQ).

Таким образом, агент и субагент общаются как сервисы: агент формирует запрос в структурированном виде,
субагент возвращает результат в том же формате.

### Инструменты (`tools`)

В OpenCode есть понятие инструментов — набора программных утилит, которые OpenCode запускает для выполнения типовых операций:

- редактор `edit` — можно разрешить или запретить чтение и запись определенных файлов, каталогов или файлов по маске;
- консоль `bash`;
- инструмент `Git`;
- инструмент `task`;
- другие инструменты.

### `task` (задача)

`task` в OpenCode — это инструмент, с помощью которого основной агент поручает отдельную работу субагенту.

Например, основной агент может:

- запустить субагента `explore` для изучения проекта;
- передать ему подробное задание;
- получить итоговый результат;
- продолжить ту же сессию по сохраненному `task_id`.

Пример логики вызова:

```python
task(
  subagent_type="explore",
  description="Поиск API",
  prompt="Найди все REST-контроллеры и опиши их методы"
)
```

Особенности:

- субагент работает в отдельной сессии и отдельном контексте;
- основной агент получает результат, но не весь внутренний контекст субагента;
- `task_id` позволяет повторно обратиться к той же сессии;
- доступ регулируется через `permission.task` в конфигурации OpenCode;
- `task` отличается от `todowrite`: `task` запускает субагента, а `todowrite` только ведет список текущих задач;
- в проекте «Морской бой» через `task` координатор запускает двух адмиралов и сохраняет их `task_id`, чтобы каждый адмирал помнил состояние своего поля до конца игры.

### Команды

Команда — это способ запустить агента с набором параметров.

### Модели и их настройка для агентов, команд и т. п.

В OpenCode конкретную модель можно задать:

- на уровне персональной конфигурации;
- на уровне конфигурации проекта;
- для конкретного агента или субагента.

Наиболее интересна конфигурация агента, которого мы выбираем для работы в самом OpenCode через `/`, аналогично агентам `Build` и `Plan`.
Такие агенты используют контекст сессии и сохраняют в нем свои изменения.
То есть мы можем написать собственного агента для планирования, задав ему модель Astra, и в рамках этого агента выполнить все планирование.
Далее запускаем агента для генерации кода с моделью Sol.

В принципе, результат будет тем же, если мы выполним планирование с агентом `Plan` по умолчанию, выбрав его в консоли и вручную переключившись на нужную модель.
Далее таким же образом выбираем агента `Build` и переключаемся на модель Sol.

#### Задание модели на уровне конфига
```json
{
   "$schema": "https://opencode.ai/config.json",
   "model": "anthropic/claude-sonnet-4-5",
   "small_model": "anthropic/claude-haiku-4-5"
}
```
`model` — это модель, которой направляются все основные запросы агента.
`small_model` — это модель, которой поручаются внутренние рутинные задачи, чтобы не тратить ресурсы и токены мощной («дорогой») языковой модели.

Типичные примеры задач для `small_model`:

- генерация заголовков сессий/диалогов;
- создание кратких сводок (`summaries`) или работа некоторых вспомогательных агентов.

#### Задание модели для агента
```json
{
  "agent": {
    "plan": {
      "mode": "primary",
       "model": "anthropic/claude-haiku-4-20250514"
    },
    "build": {
      "mode": "primary",
      "model": "anthropic/claude-3-5-sonnet-20241022"
    },
    "my-subagent": {
      "mode": "subagent",
      "model": "anthropic/claude-haiku-4-20250514",
      "description": "Описание субагента"
    }
  }
}
```

Можно использовать возможность задавать модель для агента или субагента, а также тот факт, что агент стартует с чистой сессией, чтобы планировать работу одним агентом с дорогой моделью, затем разбивать план на небольшие части и записывать их в файлы, после чего отдавать по одному файлу на реализацию дешевой модели с минимальным контекстом.
