# PATCH-01: Объединить результат выстрела с признаком живого флота

## Goal and requirements

Сократить обмен координатора с постоянными сессиями адмиралов на один вызов для каждого выстрела: защищающийся должен возвращать результат клетки и поствыстрельный признак живого флота одним ответом `RECEIVE_SHOT`, а координатор больше не должен отправлять отдельный `IS_SHIP_EXISTS`.

Обязательные требования:

- **REQ-001.** Для каждого выстрела игровой цикл должен выполнять три вызова сессий (`DO_SHOT`, `RECEIVE_SHOT`, `SHOT_RESULT`) вместо текущих четырёх; отдельный вызов проверки живых кораблей не выполняется.
- **REQ-002.** `RECEIVE_SHOT x:y` должен после применения выстрела возвращать строго `shot_result(x:y:<miss|hit|kill>:ships_alive=<true|false>)`, где `ships_alive` отражает состояние собственных кораблей защищающегося после этого выстрела.
- **REQ-003.** `IS_SHIP_EXISTS` и ответ `ship_exists(...)` должны быть удалены из поддерживаемого протокола, ожидаемых ответов, требований к журналу и алгоритма игрового цикла.
- **REQ-004.** Координатор должен проверить совпадение координаты, допустимость результата и булева признака. В корректной активной игре `ships_alive=false` допустимо только вместе с `kill`; противоречивый ответ обрабатывается существующим механизмом ошибки протокола.
- **REQ-005.** После любого корректного ответа защищающегося координатор обязан передать результат атакующему через `SHOT_RESULT` и дождаться `shot_result_saved` до завершения игры или продолжения хода. Победный `kill` поэтому учитывается в `shots_total` и `hits`.
- **REQ-006.** После сохранения результата `miss` завершает ход; `hit` и `kill` при `ships_alive=true` дают повторный выстрел тому же игроку; `kill` при `ships_alive=false` немедленно завершает игру победой атакующего.
- **REQ-007.** Координатор по-прежнему создаёт ровно две независимые постоянные сессии `blue` и `green`, использует исходные идентификаторы до конца партии, журналирует полный обмен и не раскрывает карты или координаты кораблей.
- **REQ-008.** Аргументы и команда запуска, размеры поля, состав и размещение флота, первый игрок, определение полного раунда, лимит раундов, победа и ничья остаются без изменений.
- **REQ-009.** Оба игрока по-прежнему записывают существующую JSON-схему статистики; должно выполняться `shots_total = hits + misses`, `kill` учитывается как попадание, а `ships_alive` соответствует финальному собственному состоянию.
- **REQ-010.** Текст изменяемых инструкций остаётся русским, а имена команд, ответов и полей протокола — английскими.
- **REQ-011.** Существующая политика обработки неверного или противоречивого ответа сохраняется: координатор один раз повторяет ту же команду в той же сессии с указанием ожидаемого формата, затем останавливает игру и по возможности запрашивает статистику ничьей.

## Scope and constraints

- Allowed changes: только синхронное изменение общего протокола в `AGENTS.md`, потребителя протокола в `.ai_files_dir/agents/battle-field.md` и производителя ответа в `.ai_files_dir/agents/admiral.md`.
- Architecture and code-design constraints: сохранить текстовый протокол «одна команда — один строгий ответ»; переиспользовать `DO_SHOT`, `RECEIVE_SHOT`, `SHOT_RESULT`, `PRINT_STAT` и формат `x:y`; состояние флота вычисляет только защищающийся; статистику выстрелов обновляет только атакующий при `SHOT_RESULT`; координатор обязан дождаться `shot_result_saved` до использования `ships_alive`; все три файла должны описывать один и тот же формат и порядок.
- Security/data/history/compatibility constraints: не создавать новые сессии; использовать исходные постоянные идентификаторы `blue` и `green`; не раскрывать карты или координаты кораблей; объединённый ответ содержит только координату выстрела, `miss`/`hit`/`kill` и агрегированный булев признак; сохранить `/sea-battle [field_size] [round_count]`, правила игры, журнал и JSON-схему статистики; инструкции писать по-русски, команды и структуры — по-английски; не читать и не изменять `AGENTS.md.bak`; не выполнять `git add`, `git commit` или откат существующих изменений.
- Out of scope: объединение `DO_SHOT` с `SHOT_RESULT`, пакетные выстрелы, изменение стратегии или правил игры, изменение статистики, `opencode.json`, `.ai_files_dir/commands/sea-battle.md`, README-файлы, mass-agent workflow, добавление движка или тестового фреймворка.

## Verified code context

- `AGENTS.md`, раздел `Протокол агентов`, сейчас перечисляет `INIT`, `DO_SHOT`, `RECEIVE_SHOT`, `SHOT_RESULT`, `IS_SHIP_EXISTS`, `PRINT_STAT`. Здесь находится общий контракт проекта; правила постоянных сессий, приватности и статистики уже заданы в соседних разделах.
- `.ai_files_dir/agents/battle-field.md`, разделы `Протокол`, `Журнал команд`, `Игровой цикл`: координатор сейчас ожидает `shot_result(x:y:<miss|hit|kill>)`, после `shot_result_saved` отдельно отправляет защищающемуся `IS_SHIP_EXISTS` и ветвится по `ship_exists(...)`. Общая обработка некорректного ответа уже предусматривает одну повторную отправку той же команды в той же сессии.
- `.ai_files_dir/agents/admiral.md`, разделы `RECEIVE_SHOT`, `SHOT_RESULT`, `IS_SHIP_EXISTS`: защищающийся уже знает состояние всех собственных кораблей после записи принятого выстрела, но возвращает только результат клетки; атакующий обновляет `shots_total`, `hits`, `misses` исключительно в `SHOT_RESULT`.
- `opencode.json` подключает `battle-field.md` и `admiral.md`, ограничивает координатора двумя сессиями `admiral` и сохраняет их через `task_id`; конкретные игровые команды в адаптере не перечислены, поэтому его менять не нужно.
- `.ai_files_dir/commands/sea-battle.md` задаёт только входные аргументы. В репозитории нет исполняемого игрового движка или автоматизированных тестов; после изменения `.ai_files_dir` инструкции проекта требуют полного перезапуска OpenCode.

## Required changes

1. `AGENTS.md` — раздел `Протокол агентов`: удалить `IS_SHIP_EXISTS` из поддерживаемых команд; явно задать для `RECEIVE_SHOT x:y` объединённый строгий ответ `shot_result(x:y:<miss|hit|kill>:ships_alive=<true|false>)` и пояснить, что булево поле описывает собственный живой флот защищающегося после применения выстрела. Не менять правила игры, сессий, приватности, запуска и статистики.
2. `.ai_files_dir/agents/admiral.md` — обработчик `RECEIVE_SHOT`: после фиксации выстрела вычислять наличие хотя бы одной неповреждённой клетки собственных кораблей и возвращать `shot_result(x:y:<miss|hit|kill>:ships_alive=<true|false>)`; сохранить текущую семантику `miss`, `hit`, `kill` и не обновлять атакующие счётчики здесь. Удалить самостоятельный раздел/команду `IS_SHIP_EXISTS`; остальные команды и общий `protocol_error(...)` оставить совместимыми с новым контрактом.
3. `.ai_files_dir/agents/battle-field.md` — разделы `Протокол`, `Журнал команд`, ожидаемые ответы и пример: удалить команду `IS_SHIP_EXISTS` и ответ `ship_exists(...)`; заменить формат/пример `RECEIVE_SHOT` на объединённый ответ; журнал должен по-прежнему показывать полную отправленную команду и полный ответ, но не требовать отдельной проверки флота.
4. `.ai_files_dir/agents/battle-field.md` — `Игровой цикл`: после `RECEIVE_SHOT` разобрать и проверить координату, результат и `ships_alive`; считать `false` совместимым только с `kill`; затем обязательно отправить атакующему прежний `SHOT_RESULT x:y result` и дождаться `shot_result_saved`. После сохранения результата: при `ships_alive=false` завершить игру победой атакующего; при `true` и `hit`/`kill` повторить выстрел тем же игроком; при `true` и `miss` завершить ход. В результате каждый выстрел использует ровно три вызова сессий.
5. Во всех трёх файлах сохранить русскоязычные объяснения, англоязычные имена структур и одинаковое точное написание нового ответа. Не вносить сопутствующие редакционные изменения вне изменяемого контракта.

## Validation

Обязательные проверки в корне проекта:

1. Проверить отсутствие удалённого обмена только в трёх изменяемых контрактах:

   ```powershell
   rg -n 'IS_SHIP_EXISTS|ship_exists\(' 'AGENTS.md' '.ai_files_dir/agents/battle-field.md' '.ai_files_dir/agents/admiral.md'
   ```

   Ожидаемый результат: совпадений нет (`rg` завершится с кодом 1 именно из-за отсутствия совпадений).

2. Проверить единый новый формат:

   ```powershell
   rg -n -F 'shot_result(x:y:<miss|hit|kill>:ships_alive=<true|false>)' 'AGENTS.md' '.ai_files_dir/agents/battle-field.md' '.ai_files_dir/agents/admiral.md'
   ```

   Ожидаемый результат: формат найден в каждом из трёх файлов. Фактический пример в инструкции координатора должен иметь вид наподобие `shot_result(1:1:miss:ships_alive=true)`.

3. Просмотреть diff трёх файлов и вручную протрассировать четыре ветви после обязательного `shot_result_saved`:
   - `miss + true` — ход переходит сопернику;
   - `hit + true` — тот же игрок стреляет снова;
   - `kill + true` — тот же игрок стреляет снова;
   - `kill + false` — победа атакующего;
   - `miss/hit + false` — явно считается противоречивым протокольным ответом.

   Во всех корректных ветвях на выстрел должны приходиться только `DO_SHOT`, `RECEIVE_SHOT`, `SHOT_RESULT`, а победный выстрел должен попасть в статистику атакующего.

4. Выполнить:

   ```powershell
   git diff --check
   git status --short
   ```

   Ожидаемый результат: `git diff --check` не сообщает ошибок; `git status --short` сохраняет исходные пользовательские изменения и показывает только относящиеся к задаче новые/изменённые файлы сверх зафиксированного в PREP состояния. Ничего не индексировать и не коммитить.

Автоматизированного runtime-теста в репозитории нет. После полного перезапуска OpenCode оператор может выполнить `/sea-battle 5 100`: в журнале не должно быть `IS_SHIP_EXISTS`, каждый `RECEIVE_SHOT` должен содержать `ships_alive`, а итоговые статистики должны удовлетворять `shots_total = hits + misses`. Эта post-restart проверка не является блокирующим same-session gate для patch, потому что изменённые инструкции загружаются только при перезапуске среды.
